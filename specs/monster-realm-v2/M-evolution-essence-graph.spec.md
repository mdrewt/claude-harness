## 1. Problem / intent

Drew's r2 directive is unambiguous and binding, unlike the 2026-07-25 amendment it supersedes: fusion is removed as a feature, not repaired. Evolution becomes a real, public, subscribable directed graph — species carry a standardized `tier: u8` (0–5, monotonic, never decreases — **PROVISIONAL cap, revised 2026-08-02 from an initial 0–3 against a real full-roster target of ~500 species / 7–9 tiers; see §4**), and `EvolutionPath` edges are AND-combined gates over level, per-Affinity essence balances, and two new history stats (Trust, Quality Time) plus the existing EV pool relabeled Nutrition. Essence reuses the existing 8-variant `Affinity` enum directly — no new taxonomy. A monster earns essence from wild-battle wins (typed by the **defeated** species' Affinity; practice and PvP battles are both exempt, §2 EG2-7), a new slow player-directed `essence_train()` action, or a crystalized-essence item. Evolution is event-triggered, not a standing player action: whenever any gate-relevant value changes (essence, level, Trust, Quality-Time — via `check_and_evolve`, §2 EG2-11/12/13, added 2026-08-02 per Drew's clarification), the system checks eligibility fresh. A monster with EXACTLY ONE currently-eligible path evolves automatically, immediately, no player action or confirmation — the explicit `evolve(monster_id, to_species)` reducer exists ONLY to resolve the genuine-ambiguity case: a monster simultaneously eligible for 2+ paths never auto-resolves, and stays that way (surfaced via an active party-roster notification, EG4-8) until the player picks. All 8 essence pools zero on every successful evolution. Bond is retired entirely, its two roles (investment accumulator, evolution gate) absorbed by a new Bayesian-smoothed Trust stat. Quality Time accrues only through existing player-triggered reducers, never a scheduled tick — a hard, cross-validated constraint (`evals/no-idle-accrual.eval.mjs` Check B). Nutrition needs zero new storage — it is the existing EV system, exposed as a percentage.

`fuse()`, the `Fusion` table, `fusion.ron`, and A0's taxed-carry math (ADR-0147) are deleted outright, not repurposed — the charter's caution against inventing a "combine two same-species monsters" mechanic gratuitously is respected; nothing in Drew's directive asks for one. This milestone is schema-touching and HEAVY (redesign + schema + economy-balance, all three risk-promotion triggers hit at once); §2 below lays out a five-slice, contract-first build order so client and content work can build in parallel behind a frozen schema/type freeze — matching how the sibling ceremony (`M-postgate-evolution-fusion-hardening`) sliced its own schema-touching work.

- **EG1-6:** `game-core/src/evolution/eligibility.rs` SHALL gain a pure `eligible_evolution_paths(instance: &MonsterInstance, paths: &[EvolutionPath]) -> Vec<usize>` — REPLACING `resolve_evolution`/`evolves_to` — and SHALL factor its per-edge, 5-gate evaluation (level/essence/Trust/Quality-Time/Nutrition — the actual `evolution_path` fields per EG1-4; tier-advancement is NOT a per-edge gate value, it's enforced structurally by R5, fixed 2026-08-02 review — an earlier draft of this bullet, and the ADR's own summary, wrongly listed "tier" here and omitted Nutrition) into a separate pure helper, `path_satisfied(instance: &MonsterInstance, path: &EvolutionPath) -> bool`, that `eligible_evolution_paths` calls once per candidate edge. `evolve()` (EG2-1) SHALL call this SAME `path_satisfied` helper directly on its one targeted row rather than re-deriving equivalent logic — one shared predicate for both the "what are my options" read path and the "is this one choice valid" write path, so they cannot drift out of sync. `eligible_evolution_paths` itself is UNCHANGED in behavior (still returns the full eligible set, still powers the requirements/progress panel and the multi-choice UX, EG2-2/EG4-2) — this criterion only extracts its internals, it does not narrow what it computes. `eligible_evolution_paths` ALSO gains three pure helpers (`trust_tier_of(fav, unfav) -> TrustTier`, `quality_time_tier_of(ticks) -> u8`, `nutrition_pct_of(evs: &EVs) -> u8`) that `eligible_evolution_paths` calls internally. **All three tiers SHALL be derived internally from `MonsterInstance` fields** — none SHALL be an explicit caller-computed argument (the design's own first draft split this inconsistently across three structurally identical inputs; this criterion closes that). `trust_tier_of` SHALL apply Drew's specified Bayesian smoothing before any tier-boundary lookup: `smoothed = (fav + K) / (fav + unfav + 2*K)` with `K = 10` fixed (NOT playtest-tunable, unlike the tier-boundary numbers themselves — pre-seeding the ratio so a monster with a small action count doesn't swing to an extreme tier on one event, Drew's explicit directive) — NOT a raw `fav / (fav + unfav)` ratio. ### EG2 — HIGH: reducers (essence grant, evolve rewrite, Trust/Quality-Time triggers, event-based auto-evolution)

Evidence: `care()`/`train()` live in `server-module/src/raising.rs:69/142`; `write_back_battle_results` lives in `server-module/src/battle.rs:1004`; `evolve`/`fuse` reducers live in `server-module/src/evolution.rs`.

- **EG2-1:** `evolve(ctx, monster_id, to_species: u32)` SHALL find+`require_owner`+battle-guard+trade-escrow-guard the monster (unchanged guard shape) → marshal → look up the ONE `evolution_path` row via the EG1-4 index on `(from_species=instance.species_id, to_species)` (REJECT "no such evolution" if no row matches — this is a normal, expected rejection, e.g. player error or stale client state, not a server bug) → evaluate that ONE row's gates via `path_satisfied` (EG1-6) — freshly, server-side, on every call; nothing about eligibility is ever cached, pre-computed, or trusted from what the client asserted it saw on the requirements panel — REJECT naming the specific failing requirement if not satisfied → call the shared `apply_evolution(ctx, monster_id, path)` helper (EG2-11 — factored out so this reducer and `check_and_evolve`'s auto-trigger path, EG2-11/12, both apply an evolution through exactly one code path, never two). **This reducer is now reachable, in practice, ONLY for the genuine multi-path-eligible case** — a monster with exactly one eligible path evolves automatically the instant it becomes eligible (EG2-11/12), before a player could ever call this reducer for it; a call naming a `to_species` that isn't part of a currently-eligible set is still correctly rejected by the existing logic above regardless of why the player is calling it, so no special-casing is needed. Then → zero all 8 essence fields and set `MonsterPub.tier` from a FRESH species lookup of the target (per EG1-8's fresh-lookup sourcing pattern) → dual-write. Trust and Quality-Time fields SHALL NOT be reset (lifetime history, not "spent" the way essence is). This SHALL evaluate only the one matched edge's gates, NOT the full `eligible_evolution_paths` set for the monster's current species — at up to 10 outgoing edges per species (full-roster scale), re-deriving and discarding 9 irrelevant edges' worth of gate checks on every evolve() call is pure waste once a targeted, indexed lookup is available; `eligible_evolution_paths` remains the correct (and unchanged) tool for the panel/multi-choice query, which genuinely needs the full set.
- **EG2-2 (proof-of-teeth):** WHEN two `EvolutionPath`s are simultaneously eligible for the same monster, `eligible_evolution_paths` SHALL return BOTH indices, not a single first-match winner — a positive pinned fixture with two concurrently-satisfied paths sharing one `from_species` (directly avoids the Tamagotchi/Wurmple/1997-Digivice "silent race" anti-pattern).
- **EG2-3:** `essence_train(ctx, monster_id, affinity: Affinity)` SHALL be new: ownership+battle-guard+trade-escrow guard (mirrors `care`); cooldown-gated via `last_essence_train_at_ms` (proposed 5h, playtest-tunable); grants a flat amount (proposed 5) of the player-chosen `affinity` via `saturating_add`; calls `accrue_quality_time`.
- **EG2-4:** `consume_crystalized_essence(ctx, monster_id, item_id)` SHALL be new — B2's reducer-shape successor: FULL guard set (ownership, both-role battle guard, monster trade-escrow, AND item trade-escrow — the item-escrow guard is non-optional; an earlier design draft omitted it, a real double-spend-shaped gap this criterion closes), PLUS the SAME cooldown gate `essence_train` uses (`last_essence_train_at_ms` — item-consumption and training share one clock, so a player cannot chain-consume purchased items with zero time-gating; no new storage needed). Decision-before-consume: REJECT unless `ItemDef.essence_affinity.is_some()` AND the shared cooldown has elapsed, with the item NOT consumed on either reject → `consume_one(item_id)` → grant `essence_amount` of `essence_affinity` via `saturating_add` → update `last_essence_train_at_ms`.
- **EG2-5:** `care(ctx, monster_id)` SHALL increment `trust_favorable_count` (replacing the deleted `bond += 5` write), change-triggered-recompute `MonsterPub.trust_tier`, and call `accrue_quality_time`.
- **EG2-6:** `train(ctx, monster_id, food_item_id)` SHALL remain MECHANICALLY UNCHANGED as the sole EV/Nutrition-granting path (no new EV logic — it already matches the binding constraint), gaining only a change-triggered `MonsterPub.nutrition_pct` recompute and an `accrue_quality_time` call.
- **EG2-7:** `write_back_battle_results` SHALL, on a wild-battle win (non-practice, non-PvP), grant `max(1, loser_bst / 30)` essence of the **defeated** species' Affinity to each winning active-participant monster (typed by the loser, not the winner — the "go fight the type you need" strategy; the divisor is deliberately 3x steeper than `battle_currency_reward`'s `loser_bst / 10` — essence is a slower evolution-pacing resource, not a currency, and reusing currency's exact rate cleared every authored threshold in 3-5 wins, a real undertuning risk); on a wild-battle faint (non-practice, non-PvP), increment `trust_unfavorable_count`; on a wild-battle win, credit Trust-favorable capped once/monster/rolling-24h via `trust_favorable_battle_day_epoch`; call `accrue_quality_time` for winning participants. ALL THREE (essence grant, Trust-credit, Quality-Time-credit) SHALL be BOTH practice-battle- AND PvP-battle-exempted (wild battles only) — the PvP exemption closes a collusion-farming vector two colluding accounts could otherwise exploit via repeated `challenge_pvp` rematches (no rematch cooldown exists in `pvp.rs` today), mirroring the existing practice-XP exemption and this milestone's own stated Trust design intent (ADR-0019's 2026-08-02 amendment).
- **EG2-8:** `accrue_quality_time(ctx, monster_id)` SHALL be a shared helper, added to `evals/no-idle-accrual.eval.mjs`'s `GROWTH_WRITERS` allowlist, called DIRECTLY (never transitively) from exactly five reducers, all landing in this slice's single PR (not split across parallel work): `care`, `train`, `essence_train`, `write_back_battle_results`, and the existing player-triggered movement-intent reducer (the non-scheduled move-input reducer — exact symbol confirmed at implementation time, distinct from the scheduled `movement_tick` driver).
- **EG2-9 (hard invariant, proof-of-teeth — corrected 2026-08-02, an earlier draft mischaracterized the mechanism this mirrors):** `accrue_quality_time`/`check_and_evolve` SHALL NEVER be called DIRECTLY from any scheduled reducer's own body — a dedicated companion test pins this, matching `no-idle-accrual.eval.mjs` Check B's ACTUAL semantics (direct-call-only, NOT true transitive-reachability scanning — Check B is deliberately confined this way because `write_back_battle_results`, a `GROWTH_WRITERS` entry, is ALREADY intentionally transitively reachable from the scheduled `movement_tick` reducer via the grass-encounter→battle→level-up path, and a naive transitive scan would false-positive on that legitimate path). Given `check_and_evolve` lands inside `write_back_battle_results` (EG2-12), and `write_back_battle_results` is ALSO transitively reachable from the scheduled `pvp_deadline_reaper` reducer (via `apply_pvp_forfeit`→`settle_pvp_battle`), a true "never transitively reachable" claim would be FALSE as written — the actual, buildable guarantee is direct-call-only. The reachability that DOES exist is harmless in practice: EG2-7 already gates essence/Trust/Quality-Time credit to wild-battle-only (practice- and PvP-exempt), so nothing scheduled can actually GRANT anything through this path even though it can reach the function — that exemption, not a callgraph check, is the real mechanism preventing idle accrual via `pvp_deadline_reaper`.
- **EG2-10 (proof-of-teeth):** a wrong-item application of `consume_crystalized_essence` (an item with `essence_affinity: None`, or one that ALSO satisfies an unrelated gate) SHALL be rejected with the item NOT consumed; an unowned-monster application SHALL be rejected — reducer-security parity with `evolve`'s existing test shape.
- **EG2-11 (event-based auto-evolution, added 2026-08-02 per Drew's clarification):** `server-module/src/evolution.rs` (corrected 2026-08-02 — an earlier draft wrongly placed this in `game-core/src/evolution/eligibility.rs`, the PURE/DB-free layer; `apply_evolution` takes `ctx` and performs a dual-write, so it belongs in the same ctx/DB-touching layer as `check_and_evolve`, not alongside `eligible_evolution_paths`/`path_satisfied`) SHALL gain `apply_evolution(ctx, monster_id, path: &EvolutionPathRow)` — the transform-and-write logic EG2-1 already performs (call `game_core::evolve`, zero essence, set `MonsterPub.tier` from a fresh species lookup, dual-write, leave Trust/Quality-Time untouched) factored into ONE shared helper, called by BOTH `evolve()` (EG2-1, the disambiguation-only path) and the new `check_and_evolve` (below) — an evolution is NEVER applied through two different code paths. `server-module/src/evolution.rs` SHALL ALSO gain `check_and_evolve(ctx, monster_id)`: compute `eligible_evolution_paths` (EG1-6) fresh for the monster's CURRENT species; 0 eligible → no-op; EXACTLY 1 eligible → call `apply_evolution` immediately, same transaction, no player action, no confirmation (Drew's explicit directive: "the monster automatically begins evolving"); 2+ eligible → no-op server-side — deliberately NOT surfaced via any new server state (no "pending choice" table/flag); the client already computes this exact same eligible-set client-side with zero server round-trip (EG4-1), so the existing panel plus the new party-roster badge (EG4-8) are sufficient, and inventing server-side "pending" state would just be a second, redundant source of truth for something already derivable.
- **EG2-12 (call sites, added 2026-08-02):** `check_and_evolve` SHALL be called, as the LAST step (after any essence/Trust/Quality-Time/level mutation that reducer performs), from the EXACT SAME five call sites already established for `accrue_quality_time` (EG2-8): `care`, `train`, `essence_train`, `write_back_battle_results`, and the player-triggered movement-intent reducer. This is a complete covering set, not a coincidental reuse: Quality-Time is itself one of the five gate factors and already changes on every one of those five call sites, so anywhere a gate value can change, this set already has a call site — no sixth call site is needed. (`write_back_battle_results` covers essence, Trust, AND level in one place, per the confirmed live call graph: it is the sole level-up write site, `battle.rs:1142`, reached from every battle-ending path — normal wins, PvP's `settle_pvp_battle` funnel, disconnect resolution, and recruit-failure.) **Guard warning (added 2026-08-02, real risk found on review):** `check_and_evolve`/`apply_evolution` SHALL NEVER call `reject_if_in_battle`/`is_in_ongoing_battle` — unlike this codebase's default convention (every other guarded reducer in this spec, incl. `evolve()` itself, uses it). At the exact point `write_back_battle_results` calls `check_and_evolve` (per its own documented ordering invariant, `battle.rs:1027-1037`), the battle's DB row is STILL `Ongoing` — the mutating callers update it to its terminal state only AFTER `write_back_battle_results` returns. Adding the "standard" battle guard here would silently self-reject every auto-evolution triggered from the one call site that matters most (the only site covering essence+Trust+level together). The other four call sites (`care`/`train`/`essence_train`/movement-intent) are each already guarded on "not in an ongoing battle" BEFORE their own mutation, so `check_and_evolve` at their tail is guaranteed battle-clean without needing the guard itself. **Open gap, NOT resolved by this spec (flagged 2026-08-02 review, needs resolving before this slice is built):** the "player-triggered movement-intent reducer" call site inherited from EG2-8 has two unresolved problems that block it being buildable as literally stated — (1) `Character` (the table backing movement) carries no monster reference at all today, so there is currently no way to determine WHICH monster's eligibility `check_and_evolve` would even check from this call site; (2) the more literal candidate reducer (`enqueue_move`) fires per-frame during sustained movement (the client's held-key frame-loop routes through it) — running a full eligibility recomputation as its last step on every such call is a real cost concern under SpacetimeDB's single-global-mutex reducer model, not yet addressed. This is a pre-existing gap in EG2-8 (not introduced by `check_and_evolve`), newly exposed because `check_and_evolve` now depends on that same call site resolving correctly. Needs its own design pass (which reducer, which monster, whether to bound the check to only fire when a gate value actually changed) before EG2 ships — not invented here.
- **EG2-13 (chain evolution, added 2026-08-02 per Drew's clarification — "re-check immediately"):** WHEN `apply_evolution` completes (from either `check_and_evolve`'s auto-trigger or the player-invoked `evolve()` reducer), `check_and_evolve` SHALL be called again immediately, against the monster's NEW (post-evolution) species — Trust, Quality-Time, and level do NOT reset on evolution (EG2-1), so a sufficiently-advanced monster MAY legitimately qualify for its next evolution in the same moment, and per Drew's directive this SHALL cascade automatically for as long as each successive step has exactly one eligible path, stopping only at 0 eligible (chain ends) or 2+ eligible (chain stops, falls to the player-choice case, badge shown for the monster at its final post-chain species). **Proof-of-teeth (termination):** a fixture SHALL assert a multi-step chain (3 consecutive single-eligible-path tiers) resolves to the final species in one transaction with no player action, AND a dedicated test SHALL assert `check_and_evolve` cannot loop unboundedly — this is structurally guaranteed already (R5's strict tier-per-edge +1 combined with R11's tier cap bounds any chain to at most `tier_cap` steps — tightened 2026-08-02, an earlier draft said `tier_cap + 1`, one more than the true worst case of climbing from tier 0 to `tier_cap`), but the recursive/iterative call SHALL still carry an explicit hard iteration cap (e.g. `tier_cap + 2`, generous on purpose) as a defensive guard, not a bare `loop {}`, in case a future change to R5/R11 breaks that structural guarantee.
- Touches: `server-module/src/{evolution,raising,battle,movement}.rs` (+ their `_tests.rs`), `server-module/src/lib.rs` (reducer registration). **SERIAL after EG1**; disjoint from EG3/EG4 once EG1 lands (`touches:` non-overlapping).

## 4. Decisions (escalated to Drew per the ADR-0019 amendment; defaults stated so the runner isn't blocked)

Six items genuinely reversible-only-at-real-cost — two where reviewers split during the original B1–B6 synthesis, two surfaced by later review, and two more (marked 2026-08-02) surfaced by a post-ceremony review once Drew supplied real full-roster scale numbers (~500 species, 7–9 tiers, 3–10 evolutions/species) the original ceremony didn't have. All six are implemented per their stated DEFAULT in this spec (§2) so the build is never blocked. **5 of 6 CONFIRMED 2026-08-02, 1 remains open** (deliberately — the tier cap is still stated as provisional, not rejected) before this milestone is considered fully closed.

- **Bond retention. CONFIRMED 2026-08-02 by Drew: retire entirely.** Its investment-accumulator role and both its evolution-gate uses fold into Trust (majority 4-of-6 design position; Drew's directive names exactly three history stats and never mentions Bond). Was escalated because Bond is a currently-shipped, player-visible stat (raising screen, evolution gates) and reversing the deletion after implementation would have been a real re-migration, not a config flag — no longer a live concern now that it's confirmed. No spec changes needed; the design already implemented this as its default (EG1-1/EG1-2/EG1-7/EG2-5/EG4-4/EG5-6).
- **Evolution-graph visibility / spoiler-gating. CONFIRMED 2026-08-02 by Drew: fully public/visible during development, WITH a stated commitment to implement a version of spoiler-gating before production release.** The Cyber-Sleuth-style, no-spoilers requirements screen (EG4-1) stays exactly as specced for now — nothing in EG1–EG5 changes. **Technical note for whoever picks up spoiler-gating later:** `evolution_path` (EG1-4) is a fully PUBLIC table today, readable by every connected client regardless of what they've encountered — real spoiler-gating (hiding data the client never receives, not just hiding it in the UI) will need this to become an owner-scoped `#[view]` or similarly filtered surface for at least the gated portion, which is a schema/access-pattern change, not a pure client feature. Not solved now; flagging so the future work isn't surprised by it.
- **Strict tier-per-edge advancement. CONFIRMED 2026-08-02 by Drew: no skipping (R5 stays exactly as specced) — every evolution edge requires `to_species.tier == from_species.tier + 1`.** Additionally clarified: dead ends (a species that never gets an outgoing evolution path — a monster permanently stuck at that tier) are EXPLICITLY ALLOWED, and expected to be RARE. This was already structurally permitted by the existing ruleset — R10 only requires every `tier > 0` species be REACHABLE (≥1 incoming edge); nothing in R1–R12 has ever required a species to HAVE an outgoing edge — so no rule changes to §5. This is content-authoring guidance, not a new mechanic: whoever authors content for a rare intentional "final form below max tier" species should feel free to simply not author an outgoing edge for it; "rare" is a content-design judgment call, not an enforced ratio/threshold.
- **Full essence reset on evolution. CONFIRMED 2026-08-02 by Drew: correct as specced.** All 8 essence pools zero unconditionally on every evolution — including against the concrete species-7 collision case (7→9 free vs. 7→30 costing banked Water essence) this item was escalated over. No spec changes needed (EG2-1 already implements this default); the collision risk itself is still real and still covered by the pre-evolve-warning + post-evolve-cutscene deferred items (§6).
- **Tier cap value (added 2026-08-02).** STILL OPEN, deliberately — Drew reviewed and confirmed 2026-08-02 that this item's PROVISIONAL framing is accurate, not that a final count is now locked in. `Species.tier <= 5` (R11) — six tiers total (0–5) — remains an interim value to unblock content authoring now, sized below the actual ~500-species / 7–9-tier target on purpose. Revisit and likely raise again (a one-line rule change, no schema impact — `tier: u8` already has headroom to 255) once the final tier count is confirmed, and before content authoring approaches the current cap.
- **Trust-tier granularity ceiling. CONFIRMED 2026-08-02 by Drew: expand from 4 to 5 variants.** `TrustTier` becomes `Hostile` / `Wary` / `Neutral` / `Friendly` / `Devoted` (`Ord`-derived, ascending) — Drew's exact naming and ordering. Renames/repositions from the original 4 (`Wary`/`Neutral`/`Trusting`/`Devoted`): `Wary` moves from lowest to 2nd; `Neutral` moves from 2nd to the true middle (3rd of 5); `Trusting` is renamed `Friendly`, staying in the same relative "one below max" position; `Devoted` stays at the top; `Hostile` is new, the lowest. Implemented throughout §2: EG1-2 (schema default), EG1-5 (enum definition), EG3-3/EG3-4 (content migration, `Trusting`→`Friendly`).

| R1 | Well-formed; no duplicate `(from_species, to_species)` pair. Enforced at the content-integrity gate AND, per EG1-4 (added 2026-08-02), by a DB-level unique index — not offline-gate-only. This is also what makes `to_species` alone a sufficient, unambiguous key for `evolve()` (EG2-1); see EG1-12's contingency note if this rule is ever relaxed. |
| R2 | No self-evolution. |
| R3 | No dangling species/item/affinity references. |
| R4 | No vacuous path: reject if `min_level <= 1` AND `essence` empty AND all three history-stat gates are `None`. |
| R5 | Tier monotonicity: `to_species.tier == from_species.tier + 1`, strict, no skipping. |
| R6 | Derived-forms-not-wild: no `to_species` may appear in any encounter table. |
| R7 | `essence.len() <= 3` per path (legibility cap — the requirements panel depends on paths staying readable as one card). |
| R8 | Fan-in explicitly permitted — a POSITIVE pinned test (two paths, same `to_species`, different `from_species`, both validate cleanly), not merely un-forbidden. |
| R9 | `ItemDef.essence_affinity.is_some()` ⇒ `train_stat` and `cure_status` must both be `None`. |
| R10 | Universal reachability: every species with `tier > 0` must be the `to_species` of at least one path — the structural fix that makes another Steamveil-class orphan impossible to ship silently. |
| R11 | Tier cap: `Species.tier <= 5` (**PROVISIONAL, revised 2026-08-02** — the ceremony's original `<= 3` was sized against a 4-tier assumption made without knowing the real target; the actual full-roster target is ~500 species across 7–9 tiers, and `5` was chosen as a stated provisional value, not a final confirmed count — revisit before content authoring reaches the top of this range); combined with R5's strict +1 monotonicity, this is the structural enforcement the 2026-08-02 ADR amendment names. |
| R12 | `edge_id` well-formedness (added 2026-08-02): unique across all `EvolutionPath` content, and — like `species_id` — append-only (an `edge_id` already shipped in content SHALL NEVER be reused or reassigned to a different edge across content revisions, even if the original edge is later removed). |

Because `evolve()` takes an explicit player-chosen target rather than resolving a first-match-wins order, the "dominated/subset requirement makes a sibling branch unreachable" bug class **cannot occur under this design** — no dominance-ordering rule is needed.

## 6. Out of scope / deferred (noted, not blocking, not sent to Drew)

- All numeric constants (essence amounts, cooldowns, thresholds, tier bands) are playtest-tunable placeholders (EG2-3/EG2-4/EG2-7's proposed values, EG3's proposed RON amounts) — a dedicated balance/playtest pass owns final tuning. This does NOT cover `trust_tier_of`'s Bayesian-smoothing constant `K = 10` or its formula shape (EG1-6) — that is a structural design choice from Drew's directive, fixed, not a placeholder number.
- Rare-Candy-style tier-skip currency, and a future "combine two same-species monsters" mechanic reusing A0-style math — explicitly not built, noted as plausible future levers only, per the charter's caution against gratuitous invention.
- PvP essence/Trust/Quality-Time settlement — superseded by EG2-7's revised scope: essence, Trust, and Quality-Time credit are now practice- AND PvP-exempt (wild battles only), closing the collusion-farming vector a PvP-inclusive design would open (§2 EG2-7). This makes the prior side-A/side-B essence-parity question moot — neither side settles essence through PvP. PvP's XP (a separate growth resource, unaffected by this amendment) remains deferred for side-B per ADR-0109 D10, tracked there, not here.
- Raising state (essence, Trust, Quality-Time, level, Nutrition) transfers wholesale on trade with no reset — a pre-raised, evolve-ready monster is a tradeable commodity that lets a buyer bypass every pacing gate for that monster. Noted as a known gap, not solved here; a trade-time reset or discount needs its own reducer-level design pass in `trading.rs`, out of scope for this milestone.
- Trust's exact favorable/unfavorable taxonomy beyond the MVP pair (care success, capped battle-win, faint) — Drew's own directive calls these "suggestions," open to a later content pass.
- Pre-evolve UI warning about full essence loss — a real UX beat, out of scope for this ceremony (belongs to the `uxd` milestones). **Stakes raised 2026-08-02:** with auto-evolution (EG2-11), a single-eligible-path monster evolves with NO player action at all — unlike the old always-explicit model, the player may have zero warning before the fact now, not just no warning before a voluntary click. Doesn't change the deferral, but the `uxd` pass that eventually picks this up should treat it as more load-bearing than the original note implied.
- **Post-evolve notification + cutscene (added 2026-08-02, per Drew — directly answers the awareness gap above; both open aspects RESOLVED 2026-08-02).** WHEN any evolution completes — auto-triggered (EG2-11) OR player-chosen (`evolve()`, EG2-1) — the client SHALL surface a notification and play an evolution cutscene/transformation sequence, so the player is never left unaware that a party member changed. Still out of scope for THIS ceremony (belongs to the `uxd` milestones alongside the pre-evolve warning, same UI family), but now specified precisely enough to build directly when that milestone comes up — this is no longer a pure client feature, it needs real server-side state:
  - **Design (simplified 2026-08-02 after review — one row per PLAYER, not one row per event):** a new PRIVATE table `pending_evolution_notice` (`owner_identity: Identity` `#[primary_key]`, `entries: Vec<EvolutionRevealRow>` where `EvolutionRevealRow { monster_id: u64, from_species: u32, to_species: u32 }`) plus a matching owner-scoped `#[view] my_pending_evolution_notices`, mirroring this project's existing owner-scoped-private-data convention (same shape as `player_wallet`/`my_wallet`). `apply_evolution` (EG2-11) SHALL `.push()` one entry onto the caller's row (upserting an empty row first if none exists) in the SAME transaction as the evolution itself — Vec append order IS display order, giving chain evolution's "shown in order" requirement (EG2-13) for free, with no separate sequence field or ordering-enforcement logic needed (this reuses the `Vec<SpacetimeType>` pattern EG1-4's `essence` field already establishes in this same spec, rather than inventing a second shape). Delivery is automatic: the client subscribes to its own `my_pending_evolution_notices` row and shows entries front-to-back whenever it's safe to do so; reconnection needs no special-case logic at all — the row is simply still there, same as any other persisted state, satisfying "shown at the first available opportunity" (Drew's reconnection example) without any bespoke reconnect-handling code.
  - **ACK:** a new `ack_evolution_notices(ctx, count: u32)` reducer, ownership-validated (only the row's own `owner_identity` may call it for itself), removes the first `count` entries from the front of the Vec. The client calls this once it has actually finished showing that many cutscenes — NOT on data-receipt/subscription-sync, which only proves the data arrived, not that the player saw it. This is "at-least-once" delivery, not exactly-once: if the client shows a cutscene but crashes/disconnects before the ACK call lands, the entry is still there and gets shown again next session — a deliberate tradeoff (silently losing a narratively-significant notification is a worse failure mode than rarely re-showing one).
  - Dropped from the original draft of this note as unnecessary complexity: a multi-row table with an auto_inc `event_id` per event, and a reducer that has to reject out-of-order ACKs to enforce sequencing. The single-row/Vec design gets identical guarantees (durable, ordered, server-authoritative, ACK-confirmed) with nothing separate to get out of order in the first place.
  - This new table lands in whichever slice actually builds this (a future `uxd` milestone, not EG1) — noted here now so that milestone's schema work isn't designed from scratch without this context.
- `evolved_via_edge_id: Option<u32>` — C's retired lineage intent's one plausible cheap remnant; not built now (§3). References the durable `edge_id` (EG1-4/EG1-12), never the auto_inc `path_id`.
- **No decline/cancel affordance for auto-evolution (confirmed 2026-08-02).** Matches Drew's directive literally — a single-eligible-path evolution just happens, no confirmation step. Drew flagged a FUTURE, forward-looking idea (not built now, no schema/design impact today, recorded so it isn't lost): equippable items that freeze specific gate-relevant values from changing (e.g. an item that blocks XP/level gain, another that blocks essence consumption/accrual) — a player-facing way to intentionally delay/prevent an unwanted auto-evolution without a generic cancel button. This would need its own design pass if picked up later (how it interacts with `check_and_evolve`'s per-value checks, whether it blocks the WRITE or just the eligibility CHECK, item slot/equip mechanics that don't exist yet) — explicitly not scoped into EG1–EG5.
- **Multi-eligible-path UX at full roster scale (added 2026-08-02).** EG4-2's "present all eligible paths, never auto-resolve" requirement has only been demonstrated against 2–3 simultaneously-authored branches (species 7, 20/21 examples). At the real target (up to 10 outgoing edges per non-top-tier species), nothing about the design breaks structurally, but a 10-way choice card and a 10-row progress panel is a materially different UI problem than a 2–3-way one and hasn't been designed against. Deferred to when content authoring actually reaches species with that many branches — not blocking EG1–EG5.
- A dedicated EV-reversal ("Pomeg Berry")-style item and a food-economy tuning pass — flagged by the design as a real risk (making rare food items the *sole* Nutrition path is a departure from nearly every surveyed precedent), not solved here.

## 7. Notes for the runner

**Priority:** EG1 is a hard, non-negotiable prerequisite — nothing else in this milestone can start until it lands (it is the contract-freezing slice, not merely "first by convention"). EG2/EG3/EG4 are co-equal MEDIUM/HIGH priority and mutually fan-out-safe once EG1 merges (pairwise-disjoint `touches:`; confirm with `mr-disjoint` before pairing, per standard doctrine — advisory, never overrides toward parallel on its own).
