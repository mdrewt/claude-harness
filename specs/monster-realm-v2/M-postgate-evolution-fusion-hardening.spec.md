**Status:** scheduled (spawned by `adr/0019-evolution-fusion-model.md` 2026-07-25 amendment, via the `monster-realm-evolution-fusion-redesign` workflow: research → brainstorm → debate → judge → 4-round converge, 35 agents) · **Post-gate, un-blocked** (`blocked:playtest-gate` already lifted by `playtest-gate-decision-2026-07-25.md` §7) · **Owner:** Drew · **Decision:** ADR-0019 amended already records the direction; per-slice implementation ADR at build time (project-level, 0035+ numbering)
**Stack:** spacetimedb-game · **Project:** monster-realm · **Depends on:** M-playtest-a/b/c/c.5/d CLOSED; playtest gate run 2026-07-25.
**Full deliberation trail:** harness memory card `monster-realm-evolution-fusion-workflow-2026-07-25.md` (research across 7 comparator-game clusters, 5 brainstormed candidates, 2 adversarially-debated axes, a 3-judge panel, 4 rounds of adversarial critique-and-refine). This spec carries only the converged, implementation-ready output — read the memory card or `adr/0019-evolution-fusion-model.md`'s amendment for the "why," not just the "what."

## 1. Problem / intent

Drew's 2026-07-25 playtest report proposed replacing the fixed fusion-recipe system with a typed-energy-accumulation evolution system, reasoning that fusion "erases the individual monsters... while evolution allows the individual monsters to grow and develop." Grounding this against live code found the complaint is accurate but the underlying gap is narrower than "replace fusion with evolution": `evolve()` already carries 100% of a monster's individuality state (nickname/level/xp/IVs/nature/EVs/bond — full ADR-0019 compliance); `fuse()` correctly combines the *genetic* half (IVs via per-stat max, nature from the higher-bond parent — exactly the DQM-inheritance model ADR-0019 chose) but silently resets the *relationship* half (level→1, EVs→0, bond→default 70, nickname→`None`) on every fusion — a real, verified drift from ADR-0019's own "carry/combine... not erase" intent, not a misunderstanding of what fusion does.

This milestone does **not** build Drew's proposed typed-energy system. It fixes the actual drift (broaden `fuse()`'s field-carry the same way `evolve()` already does it) and ships Drew's own worked example (a Water-Energy-flavored evolution branch) through the evolution-trigger enum's already-live `Item(id)` variant — zero engine changes required for that part. The typed multi-energy-accumulator system is explicitly deferred pending playtest evidence that this cheaper path doesn't already satisfy H2 (divergence/attachment).

## 2. Slices, acceptance criteria (EARS) + located evidence (verified live, 2026-07-25)

### A0 — HIGH: `fuse()` field-carry fix + `fusion_eligible()` extraction (no schema, no client)

> **DELIVERED (PR #248, 2026-07-25, ADR-0147)** — all of A0-1..A0-9; `fusion_eligible` gained `(a_id, b_id)` params (MonsterInstance has no id — deviation recorded in ADR-0147); eval E3 rewritten as a forced touches-delta (its old check pinned the deleted inline self-check) and hardened to arg-identity + Result-enforcement + single-definition pins. Constants shipped as first-cut per §3 — **the ADR/PR flag the ≈54h-per-parent bond-120 reachability + max-only carry tension for Drew's balance pass.**

Evidence: `fuse()` (`game-core/src/evolution/transform.rs:69-106`) computes IVs = per-stat `max(a.iv, b.iv)` and nature from the higher-bond parent (both correct, unchanged by this slice) but hardcodes `Bond::default_bond()`, `Level::new(1)`, `EVs::zero()`, and `nickname: None` regardless of parent investment. `evolve()` (`transform.rs:28-46`) carries the equivalent fields verbatim — the asymmetry is the entire bug. The current eligibility guard chain is hand-duplicated across the real `fuse` reducer, the `fuse_seam` test double (`server-module/src/evolution_tests.rs:1865`, ~100 lines), and (after A1) a new preview reducer.

- **A0-1:** WHEN `fuse()` computes `offspring.ivs`, THE system SHALL set it to the per-stat `max(a.iv, b.iv)` — unchanged from current behavior (regression guard, not a new rule).
- **A0-2:** WHEN `fuse()` computes `offspring.bond`, THE system SHALL set it to `scale_u32(max(a.bond, b.bond), FUSION_EFFICIENCY)` where `FUSION_EFFICIENCY = 75` and `scale_u32(v, pct) = v * pct / 100`, never to `Bond::default_bond()`.
- **A0-3:** WHEN `fuse()` computes `offspring.level`, THE system SHALL set it to `max(scale_u32(avg(a.level, b.level), 75), scale_u32(max(a.level, b.level), LEVEL_RETENTION_FLOOR)).max(1)` where `LEVEL_RETENTION_FLOOR = 50` — i.e. the offspring is never below 50% of the stronger parent's level, and never below a 75%-taxed average. Pinned worked examples (proof-of-teeth, exact): `(34,10)→17`, `(12,10)→8`, `(60,10)→30`, `(100,10)→50`, `(34,34 duplicate)→25`.
- **A0-4:** WHEN `fuse()` computes `offspring.xp`, THE system SHALL set it to `xp_for_level(offspring.level)` such that `level_for_xp(offspring.xp) == offspring.level` always holds (this codebase's existing level/xp-pair invariant, silently violated by the old always-level-1 hardcode).
- **A0-5:** WHEN `fuse()` computes `offspring.evs`, THE system SHALL set each stat to `scale_u32(avg(a.evs[k], b.evs[k]), 75)`, constructed via `EVs::new(...).expect(...)` with an inline proof comment (a post-tax average of two individually-valid EV sets is always within per-stat/total caps) — never a bare zero-init.
- **A0-6:** `fuse()` SHALL gain a new parameter `chosen_nickname: Option<String>`; WHEN called with `Some(s)`, THE system SHALL set `offspring.nickname = Some(s)`. (The real reducer supplies `None` until A1's UI exists — this slice only wires the plumbing.)
- **A0-7:** A new pure `fusion_eligible(a: &MonsterInstance, b: &MonsterInstance) -> Result<(), FusionError>` SHALL reject self-fusion, and SHALL reject either parent below `MIN_FUSION_LEVEL = 10` or `MIN_FUSION_BOND = 120` (checked on raw pre-tax values). The real `fuse` reducer AND the refactored `fuse_seam` test double SHALL both delegate to this one function — the hand-duplicated guard chain in `evolution_tests.rs` SHALL be deleted, not migrated.
- **A0-8 (exploit closure, proof-of-teeth):** WHEN two `Bond=120` monsters are fused, THE offspring's bond SHALL be strictly below `MIN_FUSION_BOND` (i.e. `scale_u32(120,75)=90 < 120`), and a subsequent `fusion_eligible()` call using that offspring as a parent SHALL return `Err(BelowMinBond)` — closing a "reusable high-bond carrier" exploit that existed under the old always-reset-to-70 behavior (a bond-120 parent could be reused indefinitely; taxing bond on output forces the carrier to regrow bond via real cooldown-gated `apply_care` before reuse).
- **A0-9 (proof-of-teeth):** `fuse_seam` and `fusion_eligible()` SHALL agree on every boundary case in a shared parity-test matrix.
- Touches: `game-core/src/evolution/transform.rs`, `game-core/src/evolution/eligibility.rs` (or a new `game-core/src/evolution/mod.rs` — see Decisions), `game-core/src/evolution/m10a_gating_tests.rs`, `server-module/src/evolution.rs`, `server-module/src/evolution_tests.rs`. No schema, no client, no content. ~23 call sites across these files are signature-affected and compiler-enforced (a missed call site fails the build, cannot be silently skipped).

### B2 — MEDIUM (SPAWNED 2026-07-25 by slice B, ADR-0149 D6): make item-triggered evolution reachable

> **Why this exists:** slice B's premise ("`Item(id)` is already live") was verified FALSE at build time. `Item(id)` is *declared* in the enum and *validated* by `validate_evolution_fusion`, but no production caller ever supplies `Some(item_id)`: `compute_evolves_to` (`server-module/src/evolution.rs`) hardcodes `applied_item = None` at both of its call sites (the `evolve` reducer and `sync_content_inner`), and `evolve(ctx, monster_id)` takes no item argument. B's content therefore ships **inert** — items 4/5 are unobtainable and species 30/31 unreachable — until B2 lands. B is still worth shipping first: it is engine-free, independently reviewable, and closes the FIRST-wins ordering trap in content before any reducer can hit it.

- **B2-1:** A new `apply_evolution_item(monster_id, item_id)` reducer SHALL delegate to the SAME `resolve_evolution` the passive path uses, passing `applied_item = Some(item_id)` alongside the monster's real level/bond.
- **B2-2:** WHEN the resolved trigger is not an `Item` trigger matching `item_id`, THE reducer SHALL reject explicitly (reject-not-clamp) — it SHALL NOT fall through to a `Level`/`Bond` branch and SHALL NOT consume the item. (Slice B declares the `Item` entry FIRST in each block precisely so a level-18+ Cragling cannot resolve to the level target while holding the item; B2 must not reintroduce the hazard from the reducer side.)
- **B2-3:** ON success THE reducer SHALL `consume_one` of `item_id` and apply the same transform `evolve()` already performs.
- **B2-4:** The two trigger items SHALL be stocked in shop 1 at `buy_price = sell_price * 5 / 2 = 500` (the shop file's documented 40% convention), landing in the SAME PR as the reducer so the item is never buyable-but-useless.
- **B2-5:** Spritesheets for species 30/31 SHALL ship (hard prerequisite — they become reachable in this slice; `client/art-src/generate_monsters.py` pipeline, ADR-0144).
- **B2-6 (proof-of-teeth):** a wrong-item application on a monster that ALSO satisfies a level/bond branch SHALL be rejected with the item NOT consumed; an unowned-monster application SHALL be rejected (reducer-security parity with the `evolve` reducer).
- Touches: `server-module/src/evolution.rs`, `server-module/src/lib.rs` (reducer registration), `game-core/content/shops/000-core.ron`, `client/src/ui/` (Use-Item wiring), `client/public/assets/` + `client/art-src/generate_monsters.py`. Bindings regen required → SERIAL vs any schema-touching slice.

### A1 — MEDIUM (fast-follow, gated on A0, not blocking it): fusion preview + nickname UI

Evidence: `player_wallet`'s owner-scoped `#[view]` precedent (`player_conversation`, ADR-0087, also reused by `M-postgate-ux-hardening` ux2) is the established pattern for "let a player see a preview of something before committing," and A0 leaves `chosen_nickname` wired but unreachable from the client.

- **A1-1:** WHEN a player calls a new `preview_fuse(a_id, b_id)` reducer, THE system SHALL evaluate the SAME `fusion_eligible()` the real `fuse` reducer uses and write a private `fusion_preview` row (owner-keyed, overwritten in place — no TTL reaper needed, unlike append-only precedents) visible only to that player via a new owner-scoped `#[view] my_fusion_preview`.
- **A1-2:** THE `my_fusion_preview` row's field set SHALL be a strict subset of `monster_pub`'s field set (species_id, level, bond, current_hp, derived_stats) — IVs/EVs/nature SHALL NEVER appear in the preview, matching the existing private-vs-public monster-row boundary.
- **A1-3:** THE client fusion confirm screen SHALL display the taxed preview stats and the copy: *"Bond, level, and training all partially carry over — and all three erode further the more times you fuse the same lineage, or when combining with a less-invested partner."*
- **A1-4:** WHEN the player submits a nickname on the confirm screen, THE client SHALL pass it as the real `fuse` reducer's `nickname` argument.
- **A1-5 (proof-of-teeth):** a server-side test SHALL assert `my_fusion_preview` never leaks another identity's row (matching the existing conversation-privacy gate style) and never leaks IVs/EVs/nature. A client-side test SHALL assert the confirm-screen view model surfaces the preview fields once populated.
- Touches: `server-module/src/evolution.rs`, `server-module/src/lib.rs` (new table/view registration), `client/src/ui/evolutionView.ts`, `client/src/ui/evolutionModel.ts` (+ tests). Server schema change (new table + view) → SERIAL vs any concurrent schema-touching slice; bindings regen required.

### B — MEDIUM: item-triggered evolution content (ships Drew's worked example through existing plumbing)

Evidence: the evolution-trigger primitive (`resolve_evolution`, `game-core/src/evolution/eligibility.rs:29-45`) is FIRST-wins, declaration-order, exhaustive-match over `EvolutionTrigger::{Level(l), Bond(b), Item(id)}` with **no wildcard arm** (a compiler-enforced guard against silently missing a trigger type — already-built ADR-0061 discipline). `Item(id)` is already live and already exercised by species 1/Flameling's branch structure; `content/evolutions.ron` has 6 evolution edges across 5 species blocks, all single-branch except species 1.

- **B-1:** WHEN two of species 7 (Cragling), 8 (Shadelet), 20 (Umbraquill), or 21 (Gustwyrm) are chosen for a new branch, THE content SHALL append an `Item(id)` trigger entry to that species' EXISTING `evolutions:` list — not create a new `SpeciesEvolutions` block (mirrors species 1's already-live multi-branch pattern).
- **B-2:** Neither new branch SHALL target species 6 (Steamveil) — the existing `fusion.ron` recipe's sole output — keeping the two acquisition paths disjoint this round (see Decisions for the longer-term question).
- **B-3:** Two new consumable `ItemDef` content rows SHALL ship via the existing M13b shop-content pipeline to supply the two new trigger items. **AMENDED 2026-07-25 at build time (ADR-0149 D5):** the ItemDef rows ship in `game-core/content/items/000-core.ron` as specified, but **shop stocking is DEFERRED to slice B2** — grounding found `Item(id)` is declared-but-unreachable (`compute_evolves_to` hardcodes `applied_item = None`; `evolve(ctx, monster_id)` takes no item argument; `use_battle_item` accepts only `cure_status` items), so a stocked trigger item would be a live playtest trap: ~500 gold (≈16 wild wins) for an item every reducer rejects. `sell_price: 200` is authored now so B2's buy price follows the shop file's documented 40% convention without re-litigation.
- **B-4 (content hygiene, proof-of-teeth):** any comment added to `evolutions.ron` for this slice SHALL be a full-line comment and SHALL NOT contain the literal sequences `"species_id:"` or `"to_species:"` (ADR-0143's recorded comment-hygiene constraint for this file).
- **B-5:** THIS SLICE SHALL run as its own serial content pass — `evolutions.ron` is non-glob/single-file and content slices are NOT fan-out-safe (pt-d1 finding) — never scheduled in parallel with another content-touching slice.
- Touches: `game-core/content/evolutions.ron`, `game-core/content/000-core.ron` (or wherever the new `ItemDef` rows land per the existing M13b item-content location). Zero Rust engine changes — `EvolutionTrigger`/`EvolutionCondition`/`SpeciesEvolutions` struct shapes are unchanged.

### C — LOW (opportunistic, bundle into a future content wave): lineage/provenance display fields

Evidence: none of the current fields record a fused monster's parentage; this is purely cosmetic/display, addressing the "erasure feels total" perception even where A0 already fixes the mechanics.

- **C-1:** WHEN `fuse()` produces an offspring, THE system SHALL set `offspring.generation = max(a.generation, b.generation) + 1`.
- **C-2:** WHEN `fuse()` produces an offspring, THE system SHALL set `parent_a_species`/`parent_b_species` to `Some(a.species_id)`/`Some(b.species_id)`.
- **C-3:** A monster that is NOT the product of a fusion (wild-caught, starter, or evolved-not-fused) SHALL have `generation = 0` and `parent_*_species = None`.
- **C-4 (schema-safety, proof-of-teeth):** the new fields SHALL be appended as the LAST field(s) on `MonsterInstance` with `#[serde(default)]` and SHALL pass the existing BSATN-compat gate — per M14.5f's recorded trap ("`serde(default)`≠BSATN wire-compat"), this needs the same care as `BattleMonster.status`'s last-field precedent (M14b).
- Touches: `game-core/src/monster/types.rs`, `game-core/src/evolution/transform.rs`. Real schema change (new fields on an existing table-backed struct) — own migration discipline, sequence independently.

### deferred-energy — NOT SCHEDULED: typed multi-energy-accumulator evolution (Drew's original pitch)

- **deferred-energy-1:** IF Slice B's item-triggered content demonstrates insufficient H2 divergence/attachment signal in a future playtest THEN the typed-energy accumulator system SHALL be re-evaluated as a scoped design proposal (new brainstorm/debate pass against real evidence), not built speculatively ahead of that evidence.
- No touches — explicitly not scheduled. The evolution-trigger enum's no-wildcard-arm discipline means this deferral costs no real option value; adding a typed variant later is exactly as cheap as building it now.

## 3. Decisions

Six open questions the converged design surfaced but did not resolve unilaterally — defaults stated so the runner isn't blocked, all Drew-overridable:

- **Should `fusion.ron`/`evolutions.ron` staying disjoint (B-2) be a permanent rule or a same-round-only constraint?** DEFAULT: same-round-only, softened — no permanent rule recorded, revisit if a future content wave wants deliberate overlap.
- **Which two of species 7/8/20/21 get the new branch, and what are the two items thematically?** DEFAULT: left to content-authoring judgment at build time (elemental-energy-flavored naming, echoing Drew's original pitch, is a reasonable default framing even though the underlying mechanic is a plain item trigger).
- **Do `FUSION_EFFICIENCY=75`/`MIN_FUSION_LEVEL=10`/`MIN_FUSION_BOND=120`/`LEVEL_RETENTION_FLOOR=50` ship as first-cut defaults, or does Drew want to review them first?** DEFAULT: ship as first-cut (structurally proven exploit-closed via the worked table, not yet playtest-tuned) — treat as a balance pass candidate after the next playtest, not before.
- **Does `fusion_eligible()` live in a new `game-core/src/evolution/mod.rs`, or co-locate inside the existing `eligibility.rs` (which already owns the evolution-side `resolve_evolution`/`evolves_to` SSOT)?** DEFAULT: co-locate in `eligibility.rs` — it already frames itself as the eligibility-checking file for this module, and a sibling file risks splitting one SSOT into two without a clear reason. Implementer should make this call deliberately, not by accident (flagged, not adversarially reviewed by the workflow).
- **Is A1 a hard fast-follow immediately after A0, or does it slot into the general `M-postgate-ux-hardening`/`M-postgate-client-coverage` priority lane?** DEFAULT: the latter — A0 does not depend on A1 shipping, and A1 is the same shape of work (new table/view/reducer/confirm-screen) as that lane's other slices.
- **Is the typed-energy system evaluated again after B ships playtest signal, or shelved indefinitely?** DEFAULT: re-evaluated only if a future playtest explicitly flags weak H2 signal — no calendar trigger, no standing commitment to revisit absent that evidence.

**Not unanimous** (see `adr/0019-evolution-fusion-model.md`'s amendment): whether fusion should remain a distinct mechanic at all long-term, given its thin content footprint (1 recipe) vs. evolution's (6 blocks) — the converged design keeps fusion as a real, separate, destructive mechanic; a minority position through the critique rounds argued for graduating it to secondary/optional status. Recorded, not resolved — resurface if this milestone's own experience (or a future playtest) sharpens the question.

## 4. Out of scope

The typed multi-energy-accumulator system (deferred-energy, above). Making fusion temporary/reversible (adversarially debated and rejected — the economy-sink role and Steamveil's sole acquisition path both depend on permanence, and no candidate proposal resolved what would replace the sink). Any change to `evolve()` (it already fully honors ADR-0019 — zero changes proposed anywhere in this design). Any change to the existing `fusion.ron` recipe or any of the 6 existing `evolutions.ron` blocks' triggers/targets (B only appends new branches). Retroactive correction of already-fused monster rows (a one-time grandfather, not a backfill — no migration needed).

## 5. Notes for the runner

Priority, per the converged design's own recommendation: **A0 is HIGH priority — comparable to `M-postgate-netcode-hardening`, ahead of most other queued post-gate work.** It is a narrow, evidenced correctness fix (the bond-tax-exemption exploit and the xp/level inconsistency are genuine bugs) with a small, compiler-enforced, mechanically-verifiable migration surface and zero cross-cutting schema/client risk — the same class of "close a real gap in already-shipped mechanics" work this workspace already treats as high-priority hygiene (cf. `fix-nightly-mutants`, `nightly-mut-triage`). **B is MEDIUM priority** — cheap and high signal-to-cost, but content-only work competing for the same one-content-slice-at-a-time lane as roster waves (check `M-postgate-roster-wave-3`'s position and any live e2e-budget freezes before scheduling B adjacent to it). **A1 sits alongside `M-postgate-ux-hardening`/`M-postgate-client-coverage`**, not ahead of them — genuinely new schema/view/client surface, the same shape of work already queued there; A0 does not depend on it. **C is LOW/opportunistic** — pure display, real BSATN-schema risk for a cosmetic feature, fine to bundle into a future roster/content wave rather than scheduled standalone. **deferred-energy stays below `M-postgate-netcode-hardening`, `M-postgate-ux-hardening`, `M-postgate-client-coverage`, `M-postgate-overlay-registry`, `M-postgate-roster-wave-3`, and M20+** — the largest-scope, least-evidenced item in this whole design; do not schedule until Slice B's playtest signal exists to justify it.

Build order within this milestone: A0 first and alone (smallest, safest, unblocks nothing else but is unblocked by nothing either) → B (can run disjoint-parallel with A0 once A0 is merged, since B never touches Rust engine code) → A1 → C, opportunistically. Each slice is test-first with a proof-of-teeth per ADR-0010; reserve a project-level implementation ADR per slice at build time — verify `adr_next_free` in `mr-state.json` before reserving (146 as of 2026-07-25, unconsumed by this spec, `M-postgate-netcode-hardening.spec.md`, or `M-postgate-ux-hardening.spec.md`).
