# Spec: M-postgate-netcode-hardening — movement input responsiveness + warp-path predictor epoch guard + reconnect identity persistence

**Status:** scheduled (spawned by `playtest-gate-decision-2026-07-25.md` §7-8) · **Post-gate, un-blocked** (was `blocked:playtest-gate`; the gate has now run) · **Owner:** Drew · **Decision:** ADR at build time
**Stack:** spacetimedb-game · **Project:** monster-realm · **Depends on:** M-playtest-a/b/c/c.5/d CLOSED; playtest gate run 2026-07-25.
**Promotes:** the `M-postgate-netcode-hardening` bullet already named in `PLAN.md` §9 Phase D (M-playtest-c.5 Decision E, Drew-delegated 2026-07-20) from a one-line PLAN entry to a full spec, and adds three newly-found slices on top of it — same code region, same symptom family (input/movement feel + session continuity), found by grounding Drew's 2026-07-25 playtest report against live code AND live server telemetry (`spacetime logs`, see nh4).

## 1. Problem / intent

Drew's closed playtest (`memory/projects/PlaytestReport.md`, analyzed in `playtest-gate-decision-2026-07-25.md`) reported movement as "slippery" (overshoot on tap, stutter on release) and a hard freeze where arrow keys stopped moving the character and started scrolling the browser page instead. Grounding both against live code (`master` @ `bbc7a28`) found two distinct, concrete bugs — neither is the server's `queue full` log spam, which is a deliberate anti-flood mechanism (ADR-0052, `MOVE_QUEUE_CAP=2`, fuzz-tested in `sim-harness`) working as designed. A third, pre-existing, already-known gap (ADR-0085 warp-path predictor epoch eviction) lives in the same input/movement code and was already flagged by `ptc5f`'s red-team pass as reachable in solo play with a recommendation to consider pulling it forward — this milestone is that pull-forward.

A fourth, more severe finding surfaced only by reading the live SpacetimeDB module logs directly (`spacetime logs monster-realm-playtest`, not the `playtest_event` table, which doesn't capture connection events): **Drew's single reported session actually spanned 6 separate anonymous identities**, each granted a fresh starter monster, with zero continuity between them. The gaps between identities line up with the report's own narrative (a 13.5-minute gap right where Stage five's freeze investigation happens; a 35-second gap suggesting an immediate "did that fix it?" reload). The client never persists a reconnect token, so this is not a one-off — it happens on every page reload, and the freeze bug above (nh1) is the most likely reason Drew was reloading at all. This means the freeze bug wasn't just annoying, it was silently discarding playtest progress each time it was "fixed" by a reload — raising the severity of nh1 specifically, and adding nh4 as a direct mitigation.

## 2. Slices, acceptance criteria (EARS) + located evidence (@ `bbc7a28`, verified 2026-07-25)

### nh1 — HIGH (playtest-blocking feel): movement-suppression must call `preventDefault()`, or arrow keys get hijacked by the browser once any overlay opens

Evidence: `client/src/main.ts:1006-1023`, the movement-suppression block that skips directional input while any overlay is visible, returns on all 13 checked overlay flags **without** calling `e.preventDefault()` — unlike every other branch in the same keydown handler (e.g. the `KeyQ` quest-log-open branch at `main.ts:576-601` calls `e.preventDefault()` before its `return`). Once an overlay that nothing auto-closes (e.g. quest-log via `KeyQ`, trade via `KeyU`) is left open, every subsequent `ArrowUp/Down/Left/Right` keydown falls through to the browser's native scroll instead of being captured. `KeyW/A/S/D` have no native scroll behavior, so they silently no-op instead — consistent with Drew reporting the arrow-key symptom specifically, not WASD.

- **nh1-1:** WHEN the movement-suppression branch is taken (an overlay is visible) AND the pressed key is a movement key (`KEY_DIR[e.code] !== undefined`) OR `Space`, THE handler SHALL call `e.preventDefault()` before returning, matching every other branch in the keydown handler.
- **nh1-2 (proof-of-teeth):** a test SHALL simulate an overlay being open and a subsequent `ArrowUp` (or similar) keydown, and assert `preventDefault` was called (RED today — it isn't). A mutation check: removing the added `preventDefault()` call re-fails the assertion.
- Touches: `client/src/main.ts` (+ sibling test). Client, `main.ts` → SERIAL vs any other slice touching the keydown handler (matches the existing `main.ts` SERIAL convention from `ptc5c`).

### nh2 — HIGH (playtest-blocking feel): released movement keys must cancel already-queued-but-not-yet-committed steps

Evidence: the keyup handler (`client/src/main.ts`, ~line 1038) only calls `held.release(dir)` (`client/src/prediction/heldKeys.ts:25-27`), which mutates local held-key bookkeeping only. Grepped every call site of `predictor.clearQueue()` / `predictor.setMove()` (`client/src/prediction/predictor.ts:142-150`) in `main.ts` — neither is ever called; only `predictor.enqueue()` (via `sendIntent`, `main.ts:448`) is used. With `MOVE_QUEUE_CAP=2` (`game-core/src/world.rs:16`, mirrored client-side via `client-wasm`'s `move_queue_cap()`), releasing a direction does not cancel whatever is already queued — up to 2 already-enqueued steps always play out after release, regardless of player intent. This single mechanism explains both Drew's "quick tap overshoots by a tile" and "release causes a stutter then one more tile" complaints.

- **nh2-1:** WHEN a held movement key is released (or the player switches to a different held direction) AND no further input in that direction has been queued by player intent, THE client SHALL cancel/not-emit steps beyond what the player's actual key-hold duration implies — i.e. releasing a key SHALL stop movement at (or as close as the queue/prediction model allows to) the tile the player intended, not silently drain up to `MOVE_QUEUE_CAP` extra queued steps.
- **nh2-2:** The fix SHALL NOT desync client prediction from the server's authoritative state — whatever cancellation mechanism is used must reconcile cleanly against server rejection/acceptance of in-flight moves (reuse the existing `reconcileFromStore()` repair path rather than inventing a second one).
- **nh2-3 (proof-of-teeth):** a test SHALL simulate: press direction → hold long enough to queue 2 steps → release → assert no further step beyond what was already committed/in-flight is emitted (RED today: up to `MOVE_QUEUE_CAP` steps always drain). A companion test SHALL assert a genuinely-held key for the queue-cap duration still moves the expected number of tiles (no regression on intentional sustained movement).
- **Decision hook:** the exact cancellation mechanism (call `predictor.clearQueue()` on keyup and re-derive in-flight state; or a narrower "cancel only not-yet-sent queued entries" API) is an implementation choice — record which was chosen and why in the build-time ADR, and confirm it doesn't reintroduce the class of bug `ptc5g`'s render-snap fix or `ADR-0090`'s EWMA smoothing depend on (both consume the same predictor/queue state).
- Touches: `client/src/main.ts`, `client/src/prediction/predictor.ts` (+ sibling tests). Client, sensitive predictor path → SERIAL vs nh1/nh3 and vs any other predictor-touching slice; land after nh1 (same file, avoid rebase noise) or pair carefully.

### nh3 — LOW/MEDIUM (pre-existing, now pulled forward): warp-path `Predictor` epoch/generation guard

Evidence (unchanged since `ptc5f`, ADR-0085 amend): on an own-zone warp, `resetPredictionState()` builds a fresh `Predictor` synchronously on a live socket; reconcile restarts sequence numbers at `ackedSeq+1` — the same range as a still-unacked pre-warp op. A stale rejection's `.catch` then runs `dropRejected(seq)` against the **new** predictor and can evict a legitimate new op. `ptc5f`'s red-team pass sharpened the reachability: this is **not** contention-gated — it is reachable in **solo** play by warping while holding a movement key (`MOVE_QUEUE_CAP` is per-character; the server's `"stale seq"` rejection, `guards.rs`, is the trigger), causing a swallowed first-post-warp move / brief rubber-band. `ADR-0085` already records this as an accepted risk for the closed-playtest window with a reachability-bound pin in `predictor.test.ts`.

- **nh3-1:** `Predictor` SHALL carry an epoch/generation identifier, bumped on every `resetPredictionState()` rebuild. A rejection `.catch`'s captured epoch SHALL be compared against the live predictor's current epoch before calling `dropRejected(seq)`; a mismatch SHALL no-op instead of evicting.
- **nh3-2 (proof-of-teeth):** extend the existing reachability-pinning tests in `predictor.test.ts` (added at `ptc5f`) so the previously-accepted-risk scenario (warp while holding a key → stale-seq rejection lands post-rebuild) now asserts the legitimate new op survives, not just that the gap is reachable. A mutation check: removing the epoch guard re-fails this assertion.
- **nh3-3 (doc):** amend `ADR-0085` again to record the guard is now built — the accepted-risk window closes.
- Touches: `client/src/prediction/predictor.ts` (+ sibling test), `docs/adr/0085-*.md`. Client, sensitive predictor path → SERIAL vs nh2 (same file); sequence after nh2 lands (avoid two overlapping predictor-internals rewrites in flight at once).

### nh4 — HIGH (playtest data integrity): persist the reconnect token so a page reload resumes the same anonymous identity instead of minting a new one

Evidence: `client/src/net/connection.ts:482-486` builds the connection via `DbConnection.builder().withUri(opts.uri).withDatabaseName(opts.db).onConnect(...)` — no `.withToken(...)` call anywhere in the file (grepped), and no `localStorage`/token-persistence code exists anywhere in `net/connection.ts`. The SDK explicitly supports supplying a previously-issued token to reconnect as the same identity (`.withToken('TOKEN')`, documented in `client/node_modules/spacetimedb/README.md`), so this is a wiring gap, not a missing capability. Confirmed via live server telemetry, 2026-07-25 (`spacetime logs monster-realm-playtest`): 6 `join`/`starter_granted` pairs, one per distinct identity, strictly sequential (no two identities' activity windows overlap) across Drew's single reported session — i.e. every reload produced a brand-new character with a fresh starter and zero access to whatever was recruited/held before.

- **nh4-1:** ON a successful connection, THE client SHALL persist the identity's auth token (e.g. `localStorage`) if not already stored.
- **nh4-2:** ON building a new connection, THE client SHALL supply a previously-stored token via `.withToken(...)` if one exists, so a page reload reconnects as the SAME identity (same player/character/inventory/currency state) rather than triggering a fresh `init`/starter-grant flow.
- **nh4-3:** THE stored token SHALL be scoped/cleared appropriately for the local, single-tester, isolated-DB playtest model (ADR-0129) — e.g. do not carry a token across a `playtest-wipe` (`--delete-data`), which re-registers the owner identity and would otherwise leave a stale, now-invalid token in storage causing a confusing reconnect failure.
- **nh4-4 (proof-of-teeth):** a test SHALL assert a token is written to storage on first connect, and that a subsequent `buildConnection()` call reads and supplies it via `withToken`. A scenario test SHALL assert that after a simulated `playtest-wipe`, stale-token reconnect fails gracefully (clear + fresh join) rather than hanging or erroring opaquely.
- Touches: `client/src/net/connection.ts` (+ sibling test), possibly `docs/playtest-ops.md` (note the new persistence behavior + the wipe interaction). Client, additive to the connection-build path → mostly disjoint from nh1-nh3 (different function region of the same file family) but still SERIAL vs them out of caution (same file).

## 3. Decisions

- **Bundling nh1–nh4 in one milestone vs. splitting:** kept together because all four touch the same sensitive `main.ts`/`predictor.ts`/`connection.ts` input-and-session path and the same symptom cluster a playtester experiences as "the game fights me" — splitting would just serialize them across milestones for no benefit (they're already SERIAL against each other within this one).
- **Land nh1/nh2/nh4 before a second playtest session.** All three are found+grounded, not speculative; they directly affect both the H1/H2 measurement quality AND the validity of any future `playtest_event` data (nh4 — a reload-reset identity means a "recatch" of the same species across two identities looks like two different players' single attempts, undercounting `recatchRate`) — high priority to close before drawing further conclusions from playtest data.
- **nh3's exact epoch-guard shape is an implementation decision**, not pre-specified here (see nh2's decision hook — same applies): the build-time ADR records the chosen mechanism.
- **nh4 does not replace M21 (Accounts & authentication).** M21 is full OIDC-backed cross-device identity, explicitly post-gate and out of scope here. nh4 is a much narrower fix: persist the SAME anonymous identity's token across a same-browser reload, using a capability the SDK already exposes. No new auth system, no schema change.

## 4. Out of scope

No schema/reducer changes. No server-side movement-queue redesign — `MOVE_QUEUE_CAP=2` and the server's anti-flood rejection are working as designed and are NOT touched (Drew's "queue full" log spam is not a bug per `playtest-gate-decision-2026-07-25.md` §4 item 1; the 7,961 rejects observed in the 2026-07-25 session logs are a byproduct of nh2, not a separate defect — revisit only if nh2's fix doesn't also reduce this volume). No movement-speed/animation tuning bundled here — Drew's separate note ("player walk speed a little too fast," "NPC movement too jerky") is a data/feel-tuning question, not an input-handling bug; if Drew wants it addressed, it's a small, separate, easy slice (constant tweaks), not folded in here. No full account system (M21, unchanged, post-gate).
