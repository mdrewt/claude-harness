## Message 1 (the problem statement)
I believe the intended design is for there to be a system of menus and sub-menues that can be navigated around using the hotkeys as if they were buttons on a retro hanheld console (such as the Gameboy Advance or Nintendo DS). And, just like how the game could use the same button to do different things in different scenarios, the hotkeys would be contextual. That way a user playing the game only has to learn a relatively small number of hotkeys to play the game. And the learning curve becomes even easier by making sure the buttons make logical sense, do what the a new user would assume they do, and follow conventions established by other games in this style. The additional hotkeys can stay as shortcuts for advanced users, but they shouldn't be mandatory. I think your design falls short of that intent. For example, the arrow keys (or the WASD keys) can make the character walk/run around the current area when the focus is on the character's sprite in the game world, but those keys should change their behavior when the focus is on a menu in order to navigate and allow other contextual buttons to select the different menu options or exit/cancel/undo menu interactions. This example is not exhausive or intended to be a final spec, just to give an indication of the desired controll direction for the UI. While supporting the use of controllers is out of scope for the moment, a milestone to add that support will be planned and added at some point ion the future before the game releases and the user interactions should be designed in a way that would make controller support an easy to add feature in the future for players that prefer to use them in games like this. But I don't see how the current plan would allow a user to do tasks that are common in other games like: "Bring up the main menu and then navigate into a specific submenu to select an option, then back out of that menu and navigate to a different submenu to interact with something else, and then exit the menus and continue exploring the game world."

## Message 2 (the direction + task)
You're correct that my intent seems to be the opposite of the recorded decision with my intent closer to something like using the d-pad and virtual buttons as the primary interface, while hotkeys are optional accelerators.

I believe that the conflict comes from several factors: miscommunication, mistakes make in the initial planning and design processes, comments/decisions/documentation that are either out-of-date or will be overridden by work planned in future milestones, and not taking into account (or misunderstanding) the feedback provided by the playtests. One of the playtest feedbacks specifically mention a UI overhaul and re-design with menus, submenus, and contextual buttons. That feedback should have led to a minestone designed to implement a primary interface similar to what I am describing. If it didn't then the feedback was handled incorrectly and any design/plans/decisions created from it should be thoroughly reviewed.

Your proposed direction with virtual buttons is closer to what I want. Using the buttons on an xbox controller as an example, the minimum set of required virtual buttons to play the game could be something like a D-pad with 4 directional buttons, 4 command/interaction/contextual buttons (A, B, X, Y), left/right bumpers, a Start, and a Select Button. The expanded set of optional virtual buttons would be the other hotkeys on the keyboard that exist for acceleration. The game should come with a set of default mappings that make sense, behave like a new player would expect them to, and follow common conventions established by similar games (where those conventions make sense). However, the player/user should also be allowed to re-map/configure the controls to whatever hotkeys they want and save their idividually preferred layout. When (and if) controller support is implemented, some of those hotkeys (depending on what makes the most sense) could also be mapped to whichever additional set of buttons a given controller has (such as the xbox controller's left/right triggers, or joysticks).

With this in mind, I'd consider making some adjustments to the proposed sketch for a new spec. For example, adding the X and Y buttons (X could be the "jump" button), the left and right bumpers (the bumpers could navigate between tab navigation in menus, or they could have other behaviors depending on what's appropriate for the context), making the start button responsible for both bringing up the main menu and fully exiting out of ALL menus (returning the player to the proper screen for the current state, such as the battle screen if the player in in a battle or the world if the player is exploring), while B cancels/returns to a previous menu or performs "alternate" interaction (The A button would be the "primary" interaction), and changing the "cursor" so that it doesn't behave like a literal mouse-like cursor. Instead of the cursor, the UI would visually indicate whatever menu item is "active" (about to be selected) in some manner (take inspiration from common conventions established in similar games) with the D-pad changing which menu item is currently considered "active" and the buttons actually interacting with it. A simplistic technical implementation might have a list of menu items represented by an array (or alternative data structure) with a variable representing the index of the currently "active" element in the menu. A grid of menu items could be a 2-dimensional array with a pair of indexes, and menu "tabs" would just create an additional dimension and index. The D-pad (and potentially other buttons for extra dimentions) would change the indexes in expexted and predictable ways (moving up/down, left/right, switching tabs, looping back around when the ends of the menu are reached, or resetting the selection to the initial element when appropriate). This implementation would allow menus and controls to behave as the user expects them to but it is not the only method (or even the best method) of achieving this kind of UI, it is just for demonstration.

As for the (default) virtual button mapping to the hotkeys... my instinct is to use the WASD keys as the D-pad since that's what most people are used to for movement and a controller's D-pad is also usually used by the left hand. For the other default button mappings, the Q and E keys would be the left and right bumpers, the spacebar would be the X button for jumping, Enter would be the A button, Backspace would be the B button, Escape would be the start button, and Tab would be the select button. The Y button's mapping depends on what (if anything) the game would use it for and what hotkeys perform similar functions in other games. And since using a mouse or touch is also supported, a left click (or tap) on the game screen (to avoid issues when clicking other placed on the web page) would be an general A button press while exploring the world and an A button press *on the specific UI element* when in menus. The difference is just to prevent players from trying to interact with something in the game world (instead of what's in front of them) when their character isn't in a valid interaction position, while also allowing the player to click on menu elements without forcing them to select it using the D-pad first. Left clicks (or press and hold) would work in a similar way, just functioning as the B button instead of the A button. Gestures like swipes are out of scope for now.
